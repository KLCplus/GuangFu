# 综合分析报告平台开发说明

这份文档给负责“综合分析报告平台”的同学使用。目标是把第六个页面做成一个类似 AI 网页版对话的分析平台，支持生成、查看、导出光伏综合分析报告，同时尽量把改动限制在固定模块里，避免影响现有功能。

## 先看结论

前端页面写在：

- `web-frontend/src/views/AnalysisReport.vue`
- `web-frontend/src/api/analysis.ts`

后端业务写在：

- `backend/src/main/java/com/example/pvplatform/module/analysis/`
- `backend/src/main/java/com/example/pvplatform/persistence/entity/AnalysisReportDO.java`
- `backend/src/main/java/com/example/pvplatform/persistence/mapper/AnalysisReportMapper.java`
- `backend/src/main/resources/mapper/AnalysisReportMapper.xml`，如果需要自定义 SQL 再新增
- `backend/src/main/resources/sql/init.sql`，如果要改表结构再追加迁移 SQL

AI 或微调小模型服务写在：

- `model-service/app/routers/analysis.py`
- `model-service/app/services/analysis_agent.py`
- `model-service/app/schemas.py`

不要把综合分析报告相关代码写到 `prediction`、`model`、`weather`、`user`、`openapi` 等模块里。需要用这些模块的数据时，通过已有 service/client/mapper 调用，不要直接搬代码。

## 当前项目里已经有什么

前端已经预留了页面：

- 路由：`/reports`
- 页面文件：`web-frontend/src/views/AnalysisReport.vue`
- API 文件：`web-frontend/src/api/analysis.ts`

后端已经有基础分析报告能力：

- `POST /api/analysis/report` 生成报告
- `GET /api/analysis/reports` 查询报告历史
- `GET /api/analysis/reports/{reportId}` 查询报告详情
- 数据表：`analysis_report`

现有后端报告是规则模板生成，不是 LLM/agent。你要做的是在这个基础上升级，不要重做一套平行系统。

## 推荐功能范围

第一版建议至少完成这些：

- 左侧报告历史列表：显示标题、摘要、生成时间，支持点击查看详情。
- 中间对话式工作区：参考 AI 网页版聊天，用户输入分析需求，系统返回结构化报告。
- 右侧或下方报告预览：展示摘要、天气分析、预测分析、异常分析、建议、正文。
- 报告生成表单：选择电站、选择预测任务、输入报告标题、勾选是否包含天气/预测分析。
- 导出按钮：至少支持导出 Markdown 或 HTML，最好支持 PDF/Word 之一。
- 加载、失败、空状态：生成中、生成失败、暂无报告都要有清晰状态。

加分项：

- 支持“重新生成报告”。
- 支持“复制报告正文”。
- 支持“按时间范围分析”。
- 支持“追问”：在同一份报告下继续问“为什么功率下降”“给出运维建议”等。
- 支持保存 prompt、模型名称、输入数据摘要，方便答辩时讲清楚 agent 做了什么。

## 前端怎么写

只在 `web-frontend/src/views/AnalysisReport.vue` 实现页面主体。

只在 `web-frontend/src/api/analysis.ts` 扩展接口方法和类型，比如：

```ts
export interface AnalysisChatRequest {
  stationId: number
  taskId?: number
  message: string
  reportId?: number
}

export interface AnalysisExportRequest {
  reportId: number
  format: 'md' | 'html' | 'pdf' | 'docx'
}
```

UI 组件优先使用现有项目依赖：

- Vue 3
- TypeScript
- Element Plus
- ECharts，如果需要画趋势图

页面风格建议：

- 左侧：报告历史列表。
- 中间：对话区，用户问题在右侧，AI 回复在左侧。
- 顶部：电站、预测任务、分析类型、生成按钮。
- 报告正文：使用分段标题，不要只堆一大段文字。
- 导出按钮放在报告详情区域右上角。

不要新增一个完全独立的前端工程，不要改 `router/index.ts`，因为 `/reports` 已经接好了。

## 后端怎么写

后端只扩展 `module/analysis`。

推荐新增或扩展这些类：

- `AnalysisController.java`：增加对话、导出、重新生成接口。
- `AnalysisService.java`：保留现有规则分析逻辑，负责聚合电站、天气、预测、历史功率数据。
- `AnalysisAgentService.java`：新增，负责调用 model-service 或第三方 LLM。
- `ReportExportService.java`：新增，负责导出 Markdown/HTML/PDF/Word。
- `dto/AnalysisChatRequest.java`：新增，对话请求。
- `dto/AnalysisExportRequest.java`：新增，导出请求。
- `vo/AnalysisChatVO.java`：新增，对话响应。
- `vo/AnalysisExportVO.java`：新增，导出响应。

推荐接口：

```text
POST /api/analysis/report
GET  /api/analysis/reports
GET  /api/analysis/reports/{reportId}
POST /api/analysis/chat
POST /api/analysis/reports/{reportId}/regenerate
GET  /api/analysis/reports/{reportId}/export?format=pdf
```

导出接口可以先做简单版：

- `format=md`：返回 Markdown 文本文件。
- `format=html`：返回 HTML 文件。
- `format=pdf` 或 `docx`：时间不够可以后做，但前端按钮位置先留好。

注意权限：

- 普通用户只能看和导出自己的报告。
- 管理员可以看全部报告。
- 生成报告前必须校验用户是否有电站查看权限。
- 选择预测任务时，要校验任务属于该电站，且任务状态为 `SUCCESS`。

## AI / 小模型怎么接

推荐把 AI 能力放到 `model-service`，不要直接在 Spring Boot 里写大量 prompt 和模型推理代码。

建议新增：

```text
model-service/app/routers/analysis.py
model-service/app/services/analysis_agent.py
```

然后在 `model-service/app/main.py` 里注册 router。

模式可以二选一：

1. 接第三方 API：实现最快，适合先把页面和流程跑通。
2. 微调小模型：更适合作为项目亮点，但要保证能稳定演示。可以先 mock 一个本地 agent 响应，再替换成真实模型。

无论哪种方式，都建议输入输出结构化：

```json
{
  "question": "分析该电站最近功率下降原因",
  "context": {
    "station": {},
    "weather": {},
    "prediction": {},
    "pvDataSummary": {}
  }
}
```

返回：

```json
{
  "summary": "一句话摘要",
  "sections": [
    { "title": "天气影响", "content": "..." },
    { "title": "预测趋势", "content": "..." },
    { "title": "异常判断", "content": "..." },
    { "title": "运维建议", "content": "..." }
  ],
  "markdown": "# 综合分析报告\n..."
}
```

## 不要乱动这些地方

除非提前说明原因，否则不要改：

- `web-frontend/src/router/index.ts`：报告页路由已经存在。
- `web-frontend/src/store/user.ts`：用户登录态不要为报告页单独改。
- `backend/src/main/java/com/example/pvplatform/module/auth/`
- `backend/src/main/java/com/example/pvplatform/module/user/`
- `backend/src/main/java/com/example/pvplatform/module/prediction/`
- `backend/src/main/java/com/example/pvplatform/module/model/`
- `backend/src/main/java/com/example/pvplatform/module/weather/`
- `docker-compose.yml`
- `.env`，尤其不要提交真实 API Key。

如果确实需要新增配置，请加到 `.env.example`，并在 README 里写清楚变量名，例如：

```text
ANALYSIS_AGENT_PROVIDER=mock
ANALYSIS_AGENT_API_KEY=
ANALYSIS_AGENT_BASE_URL=
```

## 建议提交顺序

建议分小步提交，方便排查：

1. 前端静态页面：先把 `/reports` 做成完整布局，用 mock 数据展示。
2. 接现有接口：报告生成、历史列表、详情查看。
3. 后端新增 chat/export 接口骨架。
4. model-service 新增 analysis agent mock。
5. Spring Boot 调用 model-service，替换规则模板里的部分内容。
6. 前端接入对话流和导出。
7. 补测试和异常状态。

## 自测清单

提交前至少确认：

- `cd web-frontend && npm run build` 能通过。
- 报告页 `/reports` 能打开，不是空白页。
- 未登录访问会跳到登录页。
- 生成报告时参数为空有提示。
- 后端接口返回失败时前端有错误提示。
- 普通用户不能查看别人的报告。
- 导出的文件能正常打开。
- `.env` 里的真实密钥没有提交。

## 最小可交付标准

如果时间紧，至少做到：

- `/reports` 页面有 AI 对话式布局。
- 能选择电站和预测任务生成报告。
- 能展示报告历史和报告详情。
- 能导出 Markdown 或 HTML。
- AI 部分可以先用 mock agent，但接口结构要留好，后面能换成真实 API 或微调模型。

这样答辩时可以说清楚：这个模块不是普通 CRUD，而是“光伏数据上下文 + 预测结果 + 天气因素 + agent 生成报告 + 报告导出”的完整闭环。
