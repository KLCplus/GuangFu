# 光伏预测平台前端页面拆分文档

> 依据《简要说明》整理，面向前端页面、模块、数据接口与交互落地。

## 1. 项目概览

平台定位：面向光伏电站的预测、模型售卖、API、报告分析与用户服务平台。

核心使用场景：

- 选定电站后查看预测结果、天气和服务器状态。
- 按模型类型选择模型，完成预测、试用或调用。
- 在广场购买/试用 API，并在 API 页查看创建、状态和调用统计。
- 使用报告页生成电站分析报告并支持导出。
- 管理端维护用户 API、电站和模型。

基础数据与模型来源：

- 长沙某电站 2023 年 6 月至今：光伏云图与功率数据。
- 斯坦福大学 2017-2019 年：光伏云图与功率数据。
- 电站接入可从 `https://pvoutput.org/live.jsp` 选择。
- 天气数据可接当地气象局或第三方天气服务。
- 代码库参考：
  - OpenSTL：`https://github.com/chengtan9907/OpenSTL`
  - Time-Series-Library：`https://github.com/thuml/Time-Series-Library`
  - Stanford solar forecasting dataset：`https://github.com/yuhao-nie/Stanford-solar-forecasting-dataset`

## 4. PC 用户端页面说明

### U-01 看板

页面目标：作为用户进入平台后的首页，围绕“当前电站状态”和“预测信息”展示核心数据。

建议布局：

- 顶部：电站选择器、当前电站名称、更新时间。
- 主区域：预测表，展示未来时间步、预测功率/辐照度、置信状态。
- 右侧：天气情况，包括天气、温度、湿度、风速、云量等字段。
- 底部：服务器状态，包括 CPU、GPU、内存、硬盘，使用健康/告警/异常状态色。

关键交互：

- 切换电站后刷新预测表、天气和服务器状态。
- 预测表支持查看详情或跳转到报告分析。
- 服务器状态可设置自动刷新。

### U-02 模型

页面目标：让用户按模型类别选择模型，并完成模型试用或预测调用。

模型分类：

- 时序模型。
- 视频时空递归模型。
- 多模态模型。

核心模块：

- 一级分类筛选。
- 模型卡片列表。
- 模型说明区：模型简介、输入要求、输出结果、适用场景。
- 参数配置区：电站、时间范围、输入数据类型等。
- 运行结果区：图表、表格、任务状态。

说明：

- 时序模型可先按“读取过去 30 分钟，预测未来 6 个步长，每步 5 分钟”设计。
- 预测窗口和步长后续建议做成模型配置项。

### U-03 云图

页面目标：演示云图预测模型能力。

范围：

- 模型：`SimVP+GSTA`。
- 输入：10 张历史云图。
- 输出：10 张未来预测云图。

页面模块：

- 云图上传区：限制 10 张，支持预览、删除、顺序调整。
- 预测按钮：校验图片数量后发起任务。
- 输出区：按时间步展示 10 张预测云图。
- 结果操作：下载单张、批量下载、重新预测。

备注：

- 原说明中提到该能力无法做实时，因为实际无法获取实时云图。因此该页面更适合做离线上传预测或模型能力展示。

### U-04 广场

页面目标：展示和售卖 API 模型，形成“浏览 - 详情 - 试用/购买 - 调用”的闭环。

参考：

- `https://console.compshare.cn/light-gpu/model-center`
- `https://cloud.siliconflow.cn/me/models`

建议更偏向硅基流动风格：卡片清晰、标签明确、调用说明直观。

页面模块：

- 模型筛选：类别、价格、状态、关键词。
- 模型卡片：名称、分类、简介、标签、价格/额度、调用量。
- 模型详情：输入输出、调用示例、计费方式、指标说明。
- 操作区：购买、试用、查看 API 文档、复制调用示例。

注意：

- 不能只做静态列举，需要真的能发起购买/试用或至少完成模拟流程。
- 另一个页面需要能调用这里购买或创建出来的 API。

### U-05 API

页面目标：集中管理所有 API 相关能力，不拆成很多页面。

页面模块：

- API 列表。
- API 创建弹窗。
- 使用统计图表。
- 调用日志。
- 额度/余额展示。

API 列表建议字段：

| 字段 | 说明 |
|---|---|
| API 名称 | 用户创建或购买后的 API 名称 |
| 所属模型 | 对应广场中的模型 |
| Key 状态 | 启用、禁用、过期 |
| 今日调用量 | 当日调用次数 |
| 总调用量 | 累计调用次数 |
| 错误率 | 调用失败占比 |
| 平均时延 | 接口平均响应时间 |
| 创建时间 | API 创建时间 |
| 操作 | 复制 Key、启停、重置、统计、删除 |

参考：`https://platform.deepseek.com/usage`

### U-06 报告

页面目标：做成 AI 网页对话式报告平台，支持报告导出。

建议布局：

- 左侧：历史会话/历史报告。
- 中间：对话区。
- 右侧或下方：报告预览区。
- 顶部：电站、预测任务、时间范围选择。

核心能力：

- 用户输入问题或选择分析模板。
- 后端接入 API、Agent 或微调小模型。
- 生成电站运行分析、预测分析、天气影响分析、风险提示和建议。
- 支持报告导出，建议预留 PDF/DOCX。

备注：

- 原说明强调这个页面要重点做，因为“实习简历人均一个 agent 项目”。因此该页面应尽量完整，不只是普通文本生成。

### U-07 新闻

页面目标：展示天气、行业新闻或系统通知。

说明：

- 可接中国天气网或新闻网站。
- 装饰作用较强，不是核心功能。
- 如果影响主业务体验，可以弱化或删除。

建议模块：

- 新闻/通知列表。
- 类型筛选。
- 未读状态。
- 详情页或详情抽屉。

### U-08 我的

页面目标：集中管理用户相关信息。

模块：

- 基本资料：用户名、头像、邮箱、手机号等。
- 钱包：余额、充值记录、消费记录。
- 安全设置：修改密码、邮箱绑定、登录设备。
- API 权益：已购买模型、额度、到期时间。

## 5. 模型分类与展示

| 模型类别 | 模型 | 前端展示建议 |
|---|---|---|
| 时序基线 | PatchTST、DLinear、iTransformer、TimeXer、TimeMixer、TSMixer、Transformer | 作为时序预测模型集合，适合卡片组 + 参数配置 + 运行结果曲线 |
| 云图/视觉融合 | CNN+MLP、CNN+LSTM、3D-CNN+LSTM、convlstm+lstm | 突出云图输入能力，展示输入样例、视觉特征和预测结果 |
| 视频时空递归 | simvp+gsta、TAU、PredRNN、PredRNN++、ConvLSTM、E3D-LSTM、swinLSTM、sunset | 适合展示连续帧输入/输出，支持帧序列预览 |

## 6. 管理端页面拆分

管理端需要与用户端明显区分，建议使用更偏后台系统的布局：左侧导航、顶部搜索/操作区、表格为主，减少营销化卡片。

| 编号 | 页面 | 管理对象 | 核心功能 | 备注 |
|---|---|---|---|---|
| A-01 | 用户/API | 用户账号与用户 API | 用户查询、API 状态、调用量、余额/额度、禁用/恢复、日志查看 | 以 API 信息为中心，一条 API 对应一行 |
| A-02 | 电站 | 用户端首页所针对的电站 | 新增电站、编辑位置、数据源配置、天气源配置、启停状态 | 与首页电站切换联动 |
| A-03 | 模型 | 广场中的模型 | 模型名称、介绍、类别、上下架、增添、删除、价格/额度配置 | 影响广场展示 |

### A-01 用户/API

页面重点：

- 以 API 为中心展示用户使用情况。
- 一条 API 对应一行。
- 支持查看所属用户、所属模型、调用量、余额、状态和日志。

### A-02 电站

页面重点：

- 维护首页可切换的电站。
- 支持从开源平台接入，也支持手动新增。
- 配置天气来源、经纬度、容量、状态等字段。

### A-03 模型

页面重点：

- 维护广场中的模型。
- 支持新增、编辑、删除、上下架。
- 配置模型介绍、名称、类别、价格、额度、调用方式。

## 10. 实施优先级

| 优先级 | 页面/模块 | 理由 |
|---|---|---|
| P0 | 看板、模型、广场、API、报告 | 构成核心业务闭环：预测展示、模型使用、模型售卖、API 统计、报告生成 |
| P1 | 云图、我的、管理端三页 | 支撑演示亮点、账号体系和运营维护 |
| P2 | 新闻、小程序完整适配 | 偏装饰或移动端增强，可在核心链路稳定后推进 |

## 11. 待确认事项

- 时序预测输入窗口和预测步长是否最终固定，或需要在模型配置中动态维护。
- 广场是否需要真实支付/钱包扣费，还是仅实现额度购买和试用流程。
- API 页是否需要区分用户自建 API、购买模型 API、系统内置 API。
- 报告导出的格式、模板和报告字段需要进一步定义。
- 天气、新闻、电站开源平台的数据接口稳定性和可用权限需要提前验证。
- 管理端“用户/API”是否以用户为主，还是以 API 为主。按原说明建议以 API 为主。
